# 开发规范

本文档是日常编码规范。项目整体边界见 [项目架构](architecture.md)，协作与验证要求见 [AGENTS.md](../AGENTS.md) 和 [贡献指南](../CONTRIBUTING.md)。

## 目标

本项目用于接口开发，整体采用类似 Laravel 的目录约定和 CLI 体验，但代码风格遵循 Go 的直接表达，不引入 Repository、DDD、DTO/VO 等额外抽象。

## 分层

- `handler`
  - 只处理 HTTP：参数绑定、上下文提取、调用 service、输出响应
  - 自己定义 HTTP 请求与响应类型
  - 简单的一层字段映射直接写在 handler 内，不额外拆 `toXxxDetail` 这类辅助函数
  - 不直接持有数据库连接，不直接查询 model
- `service`
  - 只接收 `context.Context`
  - 负责业务逻辑、事务、聚合、任务投递
  - 优先使用 `Input` 和 `Output` 结构体
- `model`
  - 放共享 GORM 模型和可复用查询辅助
  - 不做权限判断，不做 HTTP 响应拼装

## 目录约定

```text
app/
  api/                   # cmd/main.go + internal/{handler,service,middleware,router,docs,server}
  console/               # cmd/main.go + internal/{handler,service,middleware,router,docs,server}
  worker/                # cmd/main.go + internal/{handler,task,server}
cmd/grove/               # CLI 命令按职责拆文件，仍为同一个 package main
internal/                # 配置、装配、模型、观测、共享任务协议和测试夹具
pkg/                     # 跨服务技术能力；生产代码不得依赖 app/ 或 internal/
database/                # migrations/{postgres,mysql} 与 seeds/{postgres,mysql}
docs/
web/admin-vben/apps/console/src/
  api/                   # admin.ts、user.ts、profile.ts 等资源接口
  types/                 # pagination.ts 等共享协议类型
  components/            # 跨页面组件，不导入业务 views
  views/                 # 按业务域组织，列表页使用 <资源复数>/index.vue
```

## 命名与职责

- Go 包名小写、简短；文件使用 `snake_case.go`，以实际职责命名，如 `transaction/context.go`。无需给每个文件重复加 `service` 或 `handler` 后缀。
- Go 标识符中的常用缩写保持 `ID`、`HTTP`、`URL` 大写，如 `UserID`、`HTTPClient`；JSON 与数据库字段仍为 `user_id`、`api_url`。
- 生成器会拒绝生成 `_test.go`、`_linux.go`、`_amd64.go` 等具有 Go 构建语义的生产文件，并拒绝字段转换后的名称冲突。
- TypeScript API 文件使用资源单数和 kebab-case；通用协议放 `types/`。当前登录管理员资料是 `api/profile.ts`，终端用户管理是 `api/user.ts`。
- 列表页用业务域下的 `index.vue`；具名子组件用 PascalCase，例如 `configs/components/ConfigForm.vue`。移动物理路径不改变既有 URL、路由 name 或菜单 key。
- 自定义表单由业务页面通过 `formComponent` 传入 ResourcePage，不通过字符串扫描业务目录；提交转换用 `transformPayload`，固定查询用 `fixedParams`。
- 自动发现文件的 glob 必须排除 `*.test.ts`、`*.spec.ts` 和 `__tests__/`；测试可以就近放置，但不能进入运行时加载路径。
- 在同一包内按职责拆文件即可；仅当职责形成真实依赖边界时再拆新包，不按行数机械增加层次。

## Monorepo

- 当前仓库采用单仓库模式：
  - Go 后端保留在仓库根级结构
  - 管理后台前端作为子仓目录维护在 `web/admin-vben`
- 当前已接入的前端包：
  - `web/admin-vben`
- 根目录统一使用：
  - `make admin.install`
  - `make admin.dev`
  - `make admin.build`

## 约束

- 新增管理后台模块优先使用 `go run ./cmd/grove make:module Name --fields "..."`，生成模板有回归测试，具体模块仍需补业务规则并验证
- 统一通过 `response.Success` 和 `response.Fail` 输出响应
- 请求上下文统一通过 `pkg/request` 读写
- API 与 Console 的身份校验分别在各自的 `internal/middleware`；共用令牌能力来自 `pkg/auth`
- 两端通过 `auth.ExtractBearer` 解析 `Authorization: Bearer <token>`；认证方案名称不区分大小写，裸令牌和其他认证方案不作为 Bearer 令牌接受。提取后仍须执行各自的令牌、会话与权限校验。
- 不在 handler 中创建数据库或任务客户端
- 数据库由启动或路由装配层通过 `provider.DB` 选择命名资源，再把实际连接传给 service，不把业务语义写死在数据库层
- Casbin 由启动或路由装配层通过 `provider.GetEnforcer(name)` 取出并注入，不在 handler 中自行初始化
- 运行时日志统一使用 `pkg/logger`，不要在业务代码中直接使用标准库 `log`
- 日志消息尽量使用中文；字段名保持英文 snake_case，便于机器检索
- CLI 的 `fmt.Print*` 仅用于命令行结果输出，不作为运行时日志

## 开发闭环

每个功能按以下顺序完成：

1. 先确认入口、数据真相源和现有调用链。
2. 先补能表达行为的测试，再做最小实现。
3. 同步更新路由、权限、OpenAPI、配置和文档。
4. 受影响包测试通过后，再跑全仓验证。
5. 交付时记录实际命令、结果和未验证的外部依赖。

需要数据库的测试可用 `internal/testkit.OpenDB(t, &model.X{})` 创建独立的 SQLite 数据库，测试结束后自动关闭。需要 Casbin 规则表时，再调用 `testkit.CreateCasbinTable(t, db, "console_casbin_rules")`，表结构与迁移后一致。`pkg/*` 的测试自行建库，不能依赖 `internal/`。

## 明确不做的抽象

- 单一实现不创建 Factory 或 Strategy。
- 简单 CRUD 不强制拆 Domain Service、Repository 或 DTO/VO 层。
- 不用事件替代一眼可见的直接函数调用。
- 不为了未来可能的多租户、插件或工作流提前设计运行时容器。

## 多数据库资源

- `databases.default` 仍是默认连接
- `databases.resources` 支持任意命名的额外数据库资源，例如 `orders`、`crm`、`analytics`
- 业务层需要指定资源时，由装配层通过 `provider.DB.Get("orders")` 取得对应连接后传入
- 当前只解决“多数据库资源管理”，不在框架层预设读写分离或区域路由

## Casbin

- `casbin.enforcers` 支持定义任意命名执行器
- 每个执行器可以绑定独立数据库资源和独立规则表
- 默认支持两种模型：
  - `rbac`
  - `rbac_domains`
- API 层可通过权限中间件挂载到具体路由组

## 管理后台

- 管理后台应用放在 `app/console`
- 管理后台前端放在 `web/admin-vben`
- 管理后台前后端采用同仓维护，不单独拆仓
- 当前已接入的核心能力：
  - 管理员登录、刷新令牌与登出
  - 当前管理员信息、修改密码与更新个人资料
  - 工作台概览
  - 角色列表、详情、创建、更新、删除
  - 角色 API 权限分配
  - 角色菜单权限分配
  - 管理员列表、详情、创建、更新、状态变更、重置密码、删除
  - 终端用户列表、详情、创建、更新、状态变更、软删除
  - 系统配置、站点配置
  - 文章草稿、发布、归档与软删除
  - 文件上传
  - 登录日志与操作日志
- `web/admin-vben/apps/console` 当前保留的模板页面：
  - 登录
  - 工作台
  - 系统配置、站点配置
  - 管理员管理
  - 用户管理
  - 文章管理
  - 角色权限
- 管理后台身份通过令牌验证后，按请求从数据库恢复授权状态，并写入 `request.Identity`
- 管理后台 API 权限统一通过 `console` Casbin enforcer 校验
- 管理员与角色的 Casbin `g` 关系由 `AdminService` 在创建、换角色、删除时同步维护
- `console` 当前权限模型约束：
  - API 权限标识统一为 `METHOD + path`
  - API 权限清单来自运行时受保护路由
  - 菜单真相源是前端本地路由
  - 后端只代存储 `console_roles.menu_keys`
