# 响应与错误处理规范

本文档定义 `grove` 框架层的统一响应协议、错误协议、参数校验方式，以及前端接入约定。

目标只有三个：

- 保留统一的 `code: 0 / -1` 成功失败标识
- 提供正确的 HTTP 状态码，便于前端做流程控制
- 让开发者只写少量标签和标准错误，就能得到友好的中文提示

## 设计原则

参考 Laravel 的思想，但不照搬 Laravel 的返回结构。

- 成功和失败都走统一响应出口
- 字段级错误与普通业务错误分开表达
- 请求格式错误与参数值错误分开表达
- 前端展示文案依赖 `message`
- 前端流程控制依赖 HTTP 状态码
- 字段错误统一放在 `data.errors`
- 稳定业务码统一放在 `data.error_code`
- 参数错误统一收敛为一个概念：`InvalidParams`
- 生产环境不向前端暴露底层错误细节

## 响应格式

### 成功响应

```json
{
  "code": 0,
  "message": "ok",
  "data": {},
  "request_id": "req_xxx"
}
```

说明：

- `code=0` 表示请求成功
- `message` 默认为 `ok`
- `data` 为业务返回数据
- `request_id` 用于日志排查

### 失败响应

```json
{
  "code": -1,
  "message": "请求参数校验失败",
  "data": {
    "error_code": "invalid_params",
    "errors": {
      "code": ["角色编码不能为空"]
    }
  },
  "request_id": "req_xxx"
}
```

说明：

- `code=-1` 表示请求失败
- `message` 是用户可直接展示的提示文案
- `data.error_code` 是稳定的机器可读错误码
- `data.errors` 只用于字段级错误

当 `app.debug=true` 且错误带有底层 `cause` 时，失败响应会追加调试信息：

```json
{
  "code": -1,
  "message": "系统繁忙，请稍后再试",
  "data": {
    "error_code": "internal_error",
    "debug": {
      "error": "dial tcp 127.0.0.1:5432: connect: connection refused",
      "type": "*net.OpError"
    }
  },
  "request_id": "req_xxx"
}
```

`app.debug=false` 时不会返回 `data.debug`。panic stack trace 只写入日志，不返回给前端。

## HTTP 状态码规范

### `200 OK`

请求成功。

### `400 Bad Request`

请求无法正确解析。典型场景：

- JSON 语法错误
- JSON 字段类型错误
- Query 参数类型错误
- URI 参数类型错误
- 时间范围格式错误

示例：

```json
{
  "code": -1,
  "message": "请求参数格式不正确",
  "data": {
    "error_code": "invalid_params",
    "errors": {
      "page": ["页码格式不正确"]
    }
  }
}
```

### `401 Unauthorized`

未登录或登录失效。典型场景：

- 缺少 Bearer Token
- Token 无效
- Refresh Token 无效
- 账号密码错误

### `403 Forbidden`

已登录，但无权限。典型场景：

- 权限不足
- 账号已禁用
- 角色不可用
- 系统角色不允许修改

### `404 Not Found`

资源不存在。典型场景：

- 管理员不存在
- 角色不存在
- 系统配置不存在

### `409 Conflict`

业务冲突。典型场景：

- 角色编码已存在
- 系统配置已存在
- 角色已被管理员使用

### `422 Unprocessable Entity`

请求可以解析，但参数值不合法。典型场景：

- `binding:"required"` 未通过
- `min/max/email/oneof` 未通过
- 自定义 `Validate()` 未通过
- 业务层语义校验未通过

### `429 Too Many Requests`

请求频率过高。

### `500 Internal Server Error`

未预期异常或 panic。

### `503 Service Unavailable`

基础依赖不可用。典型场景：

- 数据库未配置
- 令牌管理器未配置
- 运行时接口权限清单未加载

## 参数校验规范

参数绑定统一通过 `pkg/validation` 组件处理：

- `BindJSON`
- `BindQuery`
- `BindURI`

### 推荐写法

```go
type CreateRoleRequest struct {
    Name string `json:"name" binding:"required" label:"角色名称"`
    Code string `json:"code" binding:"required" label:"角色编码"`
}
```

### 输出效果

请求：

```json
{
  "name": "运营专员"
}
```

响应：

```json
{
  "code": -1,
  "message": "请求参数校验失败",
  "data": {
    "error_code": "invalid_params",
    "errors": {
      "code": ["角色编码不能为空"]
    }
  }
}
```

### 规则说明

- `label` 用于中文字段名展示
- 新代码只使用 `label`；历史拼写 `lebel` 不再兼容
- 参数错误统一使用 `InvalidParams()`
- 绑定失败返回 `400`
- validator 规则失败返回 `422`
- 自定义 `Validate()` 失败返回 `422`

已内置常见中文提示：

- `required`
- `email`
- `min`
- `max`
- `len`
- `gt/gte`
- `lt/lte`
- `oneof`
- `eqfield`

## 业务错误规范

业务错误统一通过 `pkg/errx` 构造，不直接返回裸 `error` 文本。

### 推荐写法

```go
return errx.Conflict().
    WithCode("role_code_exists").
    WithMessage("角色编码已存在")
```

### 常用构造器

- `InvalidParams()`
- `Unauthorized()`
- `Forbidden()`
- `NotFound()`
- `Conflict()`
- `TooManyRequests()`
- `Internal()`
- `ServiceUnavailable()`

### 约定

- `message` 给用户看
- `code` 作为稳定错误码，最终输出到 `data.error_code`
- `cause` 用于日志；仅在 `app.debug=true` 时以 `data.debug.error/type` 暴露给前端
- 参数错误虽然会区分 `400/422`，但统一使用 `InvalidParams()` 构造

## 异常处理规范

所有 panic 统一由 `internal/middleware/recovery.go` 收口，不允许业务层直接输出非标准错误结构。

panic 响应示例：

```json
{
  "code": -1,
  "message": "系统繁忙，请稍后再试",
  "data": {
    "error_code": "internal_error"
  },
  "request_id": "req_xxx"
}
```

## 前端接入规范

前端统一通过 `web/admin-vben/apps/console/src/api/request.ts` 消费后端错误。

解析工具：

- `web/admin-vben/apps/console/src/utils/http-error.ts`

解析结果包含：

- `status`
- `message`
- `errorCode`
- `fieldErrors`
- `requestId`

### 前端处理规则

- `code === 0`：按成功数据处理
- `422 + data.errors`：回填表单字段错误，不弹全局 toast
- `400`：提示参数格式错误或后端返回的具体文案
- `401`：走 token 失效处理或重新登录
- `403`：提示无权限
- `404`：提示资源不存在
- `409`：提示业务冲突消息
- `500/503`：提示系统繁忙

## 组件介绍

### Response 组件

路径：`pkg/response/response.go`

职责：

- 统一输出成功响应
- 统一输出失败响应
- 自动附带 `request_id`
- 自动把错误码写入 `data.error_code`

使用方式：

```go
response.Success(c, result)
response.Fail(c, err)
```

### Errors 组件

路径：`pkg/errx/errors.go`

职责：

- 定义标准 HTTP 错误模型
- 为业务层提供统一错误构造器
- 统一错误码、文案和状态码

### Validation 组件

路径：`pkg/validation/request.go`

职责：

- 封装请求绑定
- 封装 validator 错误翻译
- 统一 `400` 和 `422`
- 自动生成字段级中文错误

### Request Client 组件

路径：`web/admin-vben/apps/console/src/api/request.ts`

职责：

- 统一解析后端错误协议
- 统一显示错误 toast
- 统一抑制字段级错误 toast
- 保留 token 刷新与重新认证流程

## 新模块接入清单

新增接口时按下面检查：

1. 请求结构必须补齐 `label`
2. handler 统一使用 `validation.BindXxx`
3. handler 统一使用 `response.Success/Fail`
4. 业务错误必须使用 `pkg/errx`
5. 唯一冲突类错误必须提供稳定 `error_code`
6. 表单页需要支持 `data.errors` 字段回填

做到这 6 点，新模块就天然接入框架错误体系。
